**شناسه:** PIS-IMPL-000  
**نسخه:** 1.0  
**وضعیت:** مشخصات اجرایی؛ بدون تغییر کد  
**شاخه:** module's-proposal  
**مرجع معماری:** سند 09 ـ معماری مرجع یکپارچه و نقشه راه اجرایی

> این سند عمداً دامنه فاز صفر را کوچک می‌کند. هدف، افزودن زیرساخت عمومی و پیچیده نیست؛ هدف تثبیت قراردادهایی است که برای ادامه توسعه فعلی پیشران لازم‌اند.

## 1. تصمیم پایه: معماری واقعی فعلی

بررسی ساختار کد موجود نشان می‌دهد برنامه در حال حاضر **Local-first** است:

- رابط کاربری: React، TypeScript و Vite
- وب: PWA
- اندروید: Capacitor
- ذخیره‌سازی اصلی: IndexedDB با fallback به localStorage
- دسترسی داده: از طریق localStore و repositoryها
- پشتیبان‌گیری: سرویس موجود backupService
- Backend/FastAPI: پایه محدود و مستقل؛ رابط اصلی فعلی برای کارکرد روزمره به آن وابسته نیست.
- ورود کاربر، حساب سازمانی، همگام‌سازی ابری و مجوزدهی چندمستاجری در معماری اجرایی فعلی فعال نیستند.

بنابراین تا زمانی که نیاز واقعی محصول اثبات نشده است، فاز صفر نباید PostgreSQL، ORM، سیستم احراز هویت، نقش‌های سازمانی، صف پیام، event bus، microservice، اتصال ERP/MES/SCADA یا زیرساخت AI اضافه کند.

**قاعده تقدم:** تصمیم‌های Local-first در docs/architecture/architecture-fa.md و پیاده‌سازی موجود، برای فاز فعلی بر هر پیشنهاد عمومی معماری مقدم‌اند. بخش‌های چندسازمانی، APIمحور و یکپارچگی پیشرفته سند 09، قابلیت‌های احتمالی آینده‌اند؛ نه تعهد فاز صفر.

## 2. هدف و خروجی فاز صفر

### هدف
ایجاد یک قرارداد حداقلی و پایدار برای داده‌های پروژه و محاسبات، با تکیه بر مخزن محلی موجود و بدون شکستن فایل‌های پشتیبان کاربران.

### خروجی‌های لازم
1. شناسنامه کوتاه موجودیت‌ها و کلیدهای ذخیره‌سازی.
2. قواعد اعتبارسنجی ورودی و خطاهای قابل نمایش.
3. قرارداد نسخه‌بندی داده و پشتیبان.
4. آزمون‌های رگرسیون برای ذخیره‌سازی، بازیابی و محاسبات مالی موجود.
5. نقشه وابستگی برای توسعه نخستین جریان کاری عملیاتی.

### خارج از دامنه
- ورود/ثبت‌نام و مدیریت حساب
- چندشرکتی/چندمستاجری و سطح دسترسی سازمانی
- همگام‌سازی بین دستگاه‌ها
- API جدید برای هر ماژول
- پایگاه داده سروری و مهاجرت داده به آن
- موتور عمومی گردش کار یا گزارش‌ساز
- داشبوردهای تازه، AI Copilot و تحلیل پیش‌بینانه
- بازنویسی موتور مالی یا تغییر فرمول‌های موجود صرفاً برای یکدست‌سازی ظاهری

## 3. قرارداد ذخیره‌سازی حداقلی

### 3.1 زیرساخت مورد استفاده

از سرویس موجود frontend/src/core/storage/localStore.ts استفاده شود. ساخت لایه ذخیره‌سازی دوم ممنوع است.

| موضوع | تصمیم |
|---|---|
| DB | همان IndexedDB با نام pishran_store |
| Object store | همان kv |
| کلید | رشته namespaceدار |
| fallback | همان localStorage با پیشوند pishran_ |
| repository | مالک خواندن/نوشتن هر دامنه |
| export/import | استفاده از localStore و backupService موجود |
| همگام‌سازی | وجود ندارد؛ داده محلی است |

### 3.2 کلیدهای موجود که باید حفظ شوند

| دامنه | کلید | سیاست |
|---|---|---|
| پروژه‌ها | projects:list:v1 | حفظ قرارداد فعلی؛ تغییر فقط با migration |
| تنظیمات | کلیدهای settings:* | حفظ mirror محلی |
| داده‌های دامنه | namespace موجود هر feature | پیش از ساخت کلید جدید، جست‌وجوی کلیدهای فعلی الزامی است |
| پشتیبان | schema 1 و 2 | بازیابی نسخه‌های پشتیبان موجود حفظ شود |

نام کلید جدید فقط پس از بررسی repository و مصرف‌کنندگان فعلی تعیین شود. تغییر نام یا حذف کلید، بدون migration و آزمون بازیابی ممنوع است.

### 3.3 قرارداد پایه رکورد

هر موجودیت دامنه‌ای که واقعاً نیاز به ذخیره‌سازی مستقل دارد باید حداقل این فیلدها را داشته باشد:

\`\`\`ts
interface LocalEntityBase {
  id: string;
  createdAt: string; // ISO 8601
  updatedAt: string;
}
\`\`\`

فیلدهای organizationId، tenantId، approvedBy، auditTrail و شناسه‌های مشابه در فاز صفر اضافه نمی‌شوند؛ زیرا قابلیت متناظر در محصول محلی فعلی وجود ندارد.

### 3.4 قواعد ذخیره‌سازی
- زمان‌ها در مدل ذخیره‌شده ISO 8601 باشند.
- شناسه موجودیت پایدار باشد؛ نام نمایشی شناسه محسوب نمی‌شود.
- مقدار عددی در مدل محاسباتی number باشد؛ واحد و مقیاس آن در تعریف فیلد مشخص شود.
- مقادیر نمایشی مثل جداکننده هزارگان و متن فارسی در داده محاسباتی ذخیره نشوند.
- داده خام ورودی از مقدار مشتق‌شده قابل تشخیص باشد.
- repository مسئول اعتبارسنجی ساختار قبل از نوشتن است.
- صفحه UI مستقیماً به IndexedDB یا localStorage دسترسی نداشته باشد.

## 4. قرارداد حداقلی دامنه پروژه

قرارداد موجود FeasibilityProject در frontend/src/core/projects/projectRepository.ts مرجع است و نباید با مدل دوم موازی جایگزین شود.

| فیلد فعلی | نوع | قاعده |
|---|---|---|
| id | string | یکتا و پایدار |
| name | string | اجباری پس از trim؛ طول محدود و معقول |
| industry | string | از فهرست صنعت موجود |
| projectType | string? | از فهرست نوع پروژه موجود |
| steelStage | string? | فقط سازگاری با داده قدیمی/فرم‌هایی که هنوز به آن نیاز دارند |
| templateId | 'raw'? | فقط قالب فعال و پشتیبانی‌شده |
| capacity | string | در ورودی عددی اعتبارسنجی شود؛ ذخیره به‌صورت رشته فقط تا زمان مهاجرت کنترل‌شده |
| location | string | اختیاری یا اجباری مطابق فرم فعلی؛ سیاست باید یکسان باشد |
| status | draft/active/archived | فقط مقادیر مجاز |
| createdAt/updatedAt | ISO string | تولید در repository |

**محدودیت:** این فاز تغییر نوع فیلدهای ذخیره‌شده یا تغییر قرارداد projects:list:v1 را انجام نمی‌دهد؛ تغییر نوع مستلزم migration مجزا است.

### عملیات موجود و رفتار مورد انتظار

| عملیات | ورودی | خروجی | خطا/کنترل |
|---|---|---|---|
| listProjects | بدون ورودی | فهرست پروژه | داده خراب به‌صورت خام منتشر نشود؛ خطای قابل مشاهده ثبت شود |
| createProject | نام، صنعت، نوع، ظرفیت، مکان | پروژه با شناسه و زمان | نام خالی/ظرفیت نامعتبر رد شود |
| updateProject | id و patch مجاز | پروژه به‌روز | شناسه ناموجود خطای روشن بدهد |
| deleteProject | id | حذف پروژه | تأیید UI؛ عدم حذف رکورد نامرتبط |
| purgeRemovedCaseProjects | بدون ورودی | فهرست باقی‌مانده | یک‌بار اجرا، idempotent و محدود به رکوردهای بازنشسته تعریف‌شده |

پاک‌سازی داده‌های قدیمی باید آزمون داشته باشد و نباید با حذف کلی کلیدها یا پاک‌کردن همه پروژه‌ها جایگزین شود.

## 5. قرارداد ورود داده و اعتبارسنجی

برای هر فرم، فقط اعتبارسنجی‌های متناسب با فیلدهای همان فرم اجرا شوند؛ ساخت موتور عمومی rule-engine در این فاز ممنوع است.

### قواعد پایه
- رشته الزامی پس از trim خالی نباشد.
- عدد باید finite باشد؛ NaN و بی‌نهایت پذیرفته نشوند.
- حداقل/حداکثر فقط وقتی اعمال شود که در نیازمندی همان فیلد تعریف شده باشد.
- واحد ظرفیت بر اساس نوع پروژه تعیین شود و در تبدیل یا نمایش با واحد دیگر اشتباه نشود.
- تاریخ باید قابل parse و در قالب قراردادی باشد.
- خطای کاربر با پیام فارسی و اشاره به فیلد نمایش داده شود.
- داده نامعتبر نباید بی‌صدا به صفر یا مقدار پیش‌فرض تبدیل شود.

### فایل ورودی
در فاز صفر، فقط مسیرهای ورود فایل موجود حفظ و ایمن‌سازی می‌شوند. طراحی import عمومی CSV/XLSX برای همه ماژول‌ها تا زمان انتخاب یک workflow واقعی به تعویق می‌افتد.

## 6. قرارداد API

در فاز صفر **API جدیدی برای ماژول‌های عملیاتی تعریف نمی‌شود**.

API فعلی /health و /api/v1/finance/evaluate در صورت استفاده باید با آزمون قرارداد حفظ شوند؛ اما مسیر اصلی پروژه‌ها و داده محلی همچنان repository محلی است.

| مسیر | وضعیت | ورودی/خروجی |
|---|---|---|
| GET /health | موجود | وضعیت سرویس |
| POST /api/v1/finance/evaluate | موجود و محدود | سرمایه اولیه، جریان‌های نقدی سالانه، نرخ تنزیل → NPV و اطلاعات پایه |
| GET /api/v1/meta | موجود | فراداده پایه؛ فهرست ماژول‌ها نباید به‌عنوان قابلیت پیاده‌سازی‌شده تفسیر شود |

**هشدار مالی:** endpoint ساده NPV جایگزین مدل مالی کامل پیشران یا موتور COMFAR نیست. نباید محاسبات کامل پروژه به آن منتقل یا به آن تقلیل داده شود.

## 7. آزمون‌های لازم فاز صفر

### 7.1 ذخیره‌سازی
1. ذخیره و خواندن رکورد از IndexedDB.
2. رفتار fallback وقتی IndexedDB در دسترس نیست.
3. رفتار خطا هنگام غیرفعال بودن localStorage.
4. حذف کلید دقیق بدون آسیب به کلیدهای هم‌نام.
5. فهرست‌کردن فقط namespace درخواستی.
6. اطمینان از عدم نشت داده بین کلیدهای دامنه.

### 7.2 پروژه
1. ساخت پروژه معتبر.
2. رد نام خالی و ورودی نامعتبر.
3. به‌روزرسانی فقط فیلدهای مجاز.
4. خطای پروژه ناموجود.
5. حذف پروژه هدف و حفظ سایر پروژه‌ها.
6. اجرای دوباره پاک‌سازی قدیمی بدون تغییر ناخواسته.
7. حفظ پروژه‌ها پس از refresh و restart برنامه.

### 7.3 پشتیبان
1. export با schema فعلی.
2. import نسخه 1 و 2.
3. رد JSON خراب، app نامعتبر و schema پشتیبانی‌نشده.
4. رد کلید خالی، تکراری یا بیش از حد طولانی.
5. بازیابی کامل رکوردها.
6. امکان undo restore.
7. حفظ تنظیمات و داده‌های پروژه پس از export/import.
8. عدم حذف اطلاعات جاری در صورت نامعتبر بودن فایل ورودی.

### 7.4 رگرسیون مالی
- اجرای کامل npm run test:financial.
- حفظ NPV و سایر شاخص‌های موجود در موتور مالی.
- حفظ IRR، شاخص سودآوری، دوره بازگشت، جریان نقدی، بدهی و سایر خروجی‌های موجود در کد فعلی.
- مقایسه نتایج قبل و بعد با fixtureهای ثابت.
- هیچ فرمول مالی در فاز صفر بازنویسی نمی‌شود مگر خطای اثبات‌شده همراه آزمون مرجع وجود داشته باشد.

## 8. ترتیب اجرای فاز صفر

| گام | اقدام | خروجی | شرط پایان |
|---|---|---|---|
| 0.1 | موجودی‌برداری از repositoryها و کلیدهای ذخیره‌سازی | فهرست کلید و مالک | هیچ کلید جدید تکراری نباشد |
| 0.2 | افزودن/تکمیل آزمون‌های storage و project | آزمون خودکار | سناریوهای اصلی عبور کنند |
| 0.3 | آزمون backup/restore | گزارش آزمون | نسخه 1 و 2 قابل بازیابی باشند |
| 0.4 | اجرای regression مالی | گزارش تست | تمام تست‌های مالی موجود عبور کنند |
| 0.5 | ثبت قرارداد اولین workflow | سند ورودی/خروجی/محاسبه | مالک داده و مرجع عدد مشخص باشد |

گام 0.5 فقط یک workflow منتخب را پوشش می‌دهد؛ ساخت هم‌زمان تمام ۱۲ ماژول جزو فاز صفر نیست.

## 9. انتخاب اولین workflow عملیاتی

با توجه به وابستگی‌ها، نخستین جریان کاری پیشنهادی عبارت است از:

**ثبت مقدار تولید و مصرف مواد یک خط → محاسبه مقدار تولید سالم/Yield → نمایش انحراف از برنامه → ارسال داده پایه به تحلیل بهای تمام‌شده.**

این جریان فقط زمانی آغاز می‌شود که فرم و داده واقعی آن در محصول موجود یا از سوی کاربر/فایل مرجع تأمین شده باشد. تا آن زمان، فرم و داده فرضی برای پرکردن داشبورد ساخته نمی‌شود.

### معیار انتخاب
- داده ورودی در دسترس و قابل راستی‌آزمایی باشد.
- محاسبه ساده و مستقل قابل کنترل باشد.
- خروجی به تصمیم واقعی کاربر منجر شود.
- با پروژه‌ها و مدل مالی فعلی تداخل نداشته باشد.
- بدون اتصال بیرونی قابل استفاده باشد.

اگر این معیارها در جریان تولید/مواد برآورده نشوند، توسعه آن متوقف می‌ماند و workflow بعدی فقط بر اساس داده موجود انتخاب می‌شود.

## 10. Definition of Done فاز صفر

فاز صفر فقط وقتی تکمیل است که:
- قرارداد موجود storage و project مستند و بدون مدل موازی باشد.
- آزمون‌های ذخیره‌سازی، پروژه و backup/restore عبور کنند.
- npm run test:financial روی همان commit موفق باشد.
- build وب روی همان commit موفق باشد.
- هیچ API، dependency یا سرویس غیرضروری اضافه نشده باشد.
- هیچ داده نمونه یا داشبورد بدون منبع واقعی اضافه نشده باشد.
- وضعیت آزمون‌ها با SHA دقیق commit گزارش شود.

## 11. مواردی که عمداً فعلاً ساخته نمی‌شوند

| قابلیت | دلیل تعویق |
|---|---|
| احراز هویت و نقش‌های سازمانی | محصول فعلی Local-first و بدون حساب کاربری است |
| PostgreSQL و ORM | نیاز اثبات‌شده‌ای برای فاز صفر وجود ندارد |
| event bus و microservices | پیچیدگی بدون ارزش فوری |
| API برای هر ماژول | repository محلی موجود کفایت می‌کند |
| موتور عمومی KPI | هنوز مجموعه شاخص‌های واقعی و مالک‌دار تثبیت نشده |
| گزارش‌ساز عمومی | یک گزارش واقعی باید ابتدا نیاز آن را اثبات کند |
| AI Copilot | بدون داده قابل اتکا و کنترل دسترسی، ارزش قابل دفاع ندارد |
| اتصال بلادرنگ صنعتی | نیازمند سامانه و دسترسی واقعی مشتری |
| seed/demo data | خطر اشتباه‌گرفتن داده ساختگی با اطلاعات واقعی |
| داشبوردهای متعدد | ابتدا یک جریان کامل و قابل راستی‌آزمایی تحویل شود |
